# Кабинет клиники и заявки без Health24

## Что подготовлено

- `/admin/`: закрытая очередь заявок и управление часовыми окнами врачей.
- В форме сайта врачам из Health24 оставлен существующий маршрут записи. Остальным врачам доступна заявка с желаемым часовым окном после подключения Supabase.
- Пациент оставляет только имя, телефон и согласие. Дата рождения, пол и медицинские комментарии для заявки не собираются.
- Статусы: `new`, `contacted`, `confirmed`, `cancelled`. Подтверждение требует будущего согласованного времени по Киеву. Первоначальное желаемое время подставляется автоматически.
- Подтверждённый час скрывается из публичного списка. Пересекающиеся подтверждённые приёмы одного врача запрещены ограничением PostgreSQL, включая одновременные действия нескольких администраторов.
- Неподтверждённые заявки час не резервируют. Возможны несколько пожеланий на один час; администратор подтверждает одну заявку и согласовывает другое время с остальными.
- Смена статуса сама по себе не отправляет SMS, email и не звонит пациенту. Администратор сообщает результат отдельно.
- За пределами сайта приёмы этих врачей должны также заноситься администратором или закрываться через «Години прийому». Supabase не знает о записях из других систем.

## Подключение нового выделенного проекта

1. Создать отдельный проект Supabase для клиники. Пароль базы и ключи не отправлять в чат и не сохранять в Git.
2. В SQL Editor выполнить **один раз** `database/callback-requests-setup.sql` целиком. Это начальная схема нового проекта; она не предназначена для повторного применения к существующим данным. При дальнейших изменениях использовать миграции Supabase CLI.
3. В Authentication создать пользовательский аккаунт администратора с реальным email и паролем, который владелец назначает самостоятельно. Если создание требует подтверждения email, закончить подтверждение перед входом. Текущая версия кабинета поддерживает вход по email/паролю, без регистрации на публичном сайте.
4. В SQL Editor добавить **только назначенный аккаунт** в список доступа, заменив строку email:

   ```sql
   insert into public.clinic_admins(user_id)
   select id from auth.users where email = '<email администратора>'
   on conflict (user_id) do update set is_active = true;
   ```

   Проверить, что добавлена ровно одна строка. Обычный пользователь Supabase без этой записи не получает доступ к заявкам.
5. В Production переменные окружения проекта Vercel `breoris-medical-site-dist` добавить:

   - `SUPABASE_URL`: `https://<project-ref>.supabase.co`
   - `SUPABASE_PUBLISHABLE_KEY`: publishable API key
   - `SUPABASE_SECRET_KEY`: server secret API key (или legacy service-role key)

   Все три используются только серверными функциями. В файлы `dist/`, браузер и переписку ключи не помещать. Выполнить Redeploy.
6. Войти на `/admin/`, открыть «Години прийому» и задать реальные часы нужных врачей. Дубли часов не создаются; закрытые часы в указанном диапазоне повторно открываются.
7. Проверить одну согласованную тестовую заявку: сохранение, появление в кабинете, подтверждение, исчезновение часа, отмену и повторное освобождение. Тестовые контактные сведения вводить только по согласованию с клиникой.
8. Проверить реальный проект: отсутствие публичного чтения таблиц/вызова RPC; отсутствие доступа у обычного аккаунта; доступ назначенного администратора; запустить Supabase advisors. До этой проверки нельзя считать рабочее подключение завершённым.

До конфигурации Supabase в каталоге сайта не включаются новые заявки; API отклоняет попытку сохранения. Health24 продолжает работать отдельно.

## Разграничение доступа

RLS включён на всех четырёх таблицах. Роли `anon` и обычные `authenticated` не имеют доступа к сведениям пациентов. Только активный пользователь из `clinic_admins` может читать заявки, менять их статус и управлять окнами. Поля контактов нельзя редактировать обычным API администратора.

Публичная форма сохраняет заявку через сервер и RPC с серверным ключом. Повторные попытки защищены уникальным UUID и проверкой совпадения данных. Ограничение количества заявок хранится в PostgreSQL, а не в памяти Vercel: 5 на адрес за 10 минут и 3 на телефон за 30 минут. В лимитах хранятся HMAC-отпечатки; исходный IP не сохраняется.

Сессия кабинета: `HttpOnly; Secure; SameSite=Strict`, не более часа, без токенов в localStorage. Каждое обращение проверяет пользователя Supabase Auth и актуальное членство в `clinic_admins`. Для отзыва доступа установить `is_active=false` и отозвать сессию в Supabase; удаление аккаунта само по себе не следует считать отзывом всех токенов.

## Проверки перед публикацией

```sh
node --test tests/health24.test.js tests/health24-booking.test.js tests/clinic-requests.test.js
npm ci --prefix tests/database --ignore-scripts
npm test --prefix tests/database
```

Проверки базы выполняют начальную схему на локальном PGlite/PostgreSQL с расширением btree_gist и вымышленными данными. Проверяется RLS, исключение пересечений, закрытие и повторное открытие часа при смене статуса, идемпотентность и общие лимиты. Внешний Supabase ими не подменяется: рабочее подключение требует отдельной проверки после создания проекта.

Локальная проверка интерфейса 19.10.2026: выбор часового окна → заявка → кабинет → подтверждение исходного часа одной кнопкой → окно больше не предлагается. Использован отдельный тестовый HTTP-сервер без отправки в рабочую Health24 или Supabase.

Документация: [защита Data API](https://supabase.com/docs/guides/api/securing-your-api), [вход по паролю](https://supabase.com/docs/reference/javascript/auth-signinwithpassword).
